# 微信数据治理方案（面向模型训练）

> 目标：从解密后的微信数据库中，抽取**所有联系人信息**与**所有聊天记录**，
> 重建为一套干净、自洽、便于模型训练的库结构。
> **本版本已根据你的 5 项决策更新（见 §6），并新增双账号合并方案（见 §1.1、§7）。
> 下游 agent 同步改动见 `docs/下游迁移指南.md`。**

---

## 1. 总体思路

- **输入**：**两个**解密库目录（只读，不改动原始数据）：
  - `wechat-decrypt-personal/decrypted/` — 个人号（号主 wxid 见 `accounts.local.py`；messages 去重后约 236 万行）
  - `wechat-decrypt-work/decrypted/` — 工作号（号主 wxid 见 `accounts.local.py`；messages 去重后约 1.9 万行）
- **输出**：新建一个治理后的库 `governed.db`（位于项目根的 `output/`），**两号数据合并进同库**，结构清晰、字段精简。
- **原则**：
  1. 用**业务主键 `username`** 贯穿所有表，去掉微信内部的自增 `id` 中转。
  2. 用 **`account` 短标签**（`personal` / `work`）区分数据属于哪个微信账号；号主 wxid 仅在构建配置 `ACCOUNTS` 中维护，**不进 governed.db**；**所有表、所有唯一约束都带 `account` 维度**。
  3. 把 `extra_buffer`（protobuf）中有用信息**拆成独立列**（性别、地区、标签、签名）。
  4. 聊天记录**文本取正文**；非文本消息**不存原始媒体**，但**保留外链引用**，可回原始库取数据。
  5. 删除微信程序自用、对训练无价值的字段（拼音索引、压缩缓存、同步状态等）。
  6. 把分散在 1000+ 张 `Msg_<md5>` 表里的消息**合并成一张 `messages` 表**。

### 1.1 双账号合并（新增）

**为什么要加 `account`**

| 现象（已实测） | 含义 |
|----------------|------|
| 两号 `contacts.username` 有 **82 个重叠**（同 wxid、同群 `@chatroom`、同公众号 `gh_*`） | 不能把 `username` 当全局主键，否则后写入的号会覆盖前一个号的联系人/metadata |
| 两号 `messages.server_id` 抽样有 **34 个重叠** | 不能把 `server_id` 当全局唯一键；同一条公众号推送/系统消息在不同账号里可能同 svrid |
| 同一会话（如与某好友的单聊）在两个号里各有一份 | `chat_username` 必须按 **`account` scoped**：`WHERE account='personal' AND chat_username=?` |

**最小改动策略**：不新建「账号表」，只在现有 4 张表各加一列 **`account`**（短标签 `personal`/`work`），并把主键/唯一索引从单列改为 **`(account, …)`**。

**构建配置 `ACCOUNTS`**（不进 governed.db）：

```python
ACCOUNTS = [
    {"account": "personal",  "owner_wxid": "wxid_personal_owner", "decrypted_dir": ".../wechat-decrypt-personal/decrypted"},
    {"account": "work", "owner_wxid": "wxid_work_owner",     "decrypted_dir": ".../wechat-decrypt-work/decrypted"},
]
```

| 表 | 原主键/唯一键 | 新主键/唯一键 |
|----|---------------|---------------|
| `contacts` | `username` | **`(account, username)`** |
| `chatrooms` | `username` | **`(account, username)`** |
| `chatroom_members` | `(room_username, member_username)` | **`(account, room_username, member_username)`** |
| `messages` | `server_id`（部分唯一） | **`(account, server_id)`**（`WHERE server_id != 0`） |

**识别「我」**（构建脚本内，每个输入目录）：

1. **优先**：配置 `ACCOUNTS[].owner_wxid`（上表，稳定）。
2. **兜底**：`detect_self_wxid()`（私聊里出现最多、且 ≠ 对端 的发送者），结果须与配置一致或写入日志告警。

**`sender_username` / `is_self` 语义不变，但 scoped 到 `account`**：

- 在该 `account` 的消息里，自己仍记为 `sender_username='me'`、`is_self=1`。
- 下游查询某号对话：`WHERE account='personal' AND chat_username='wxid_xxx'`。
- 查「我」发的：`WHERE account='personal' AND is_self=1`（不得跨号混用 `me`）。

**引用自关联**（`reply_to`）也必须在同一号内：

```sql
SELECT q.content, o.content AS quoted
FROM messages q
LEFT JOIN messages o
  ON o.account = q.account
 AND o.server_id = q.reply_to
 AND o.server_id != 0
WHERE q.account = ? AND q.type = 'quote';
```

**媒体回查**：`media_ref` + `server_id` 不变，但回查原始库时需知道**消息来自哪个号** → 用 `account` 映射到对应 `wechat-decrypt-*/decrypted/message/`（配置项，不写入 governed.db，见 README / 构建脚本 `ACCOUNTS` 列表）。

**构建流程**（相对单号仅多一层循环）：

```
for acct in ACCOUNTS:  # personal, work
    build_contacts(acct)             # INSERT，PK (account, username)
    build_chatrooms(acct)
    build_chatroom_members(acct)
    build_messages(acct)             # INSERT OR IGNORE on (account, server_id)
backfill_reply_quote()               # JOIN 带 account
validate_contact_types()
```

重叠联系人**不合并**：同一 `wxid` 在两号各一行（备注/标签/好友关系可能不同），留给下游按 `account` 选用。

## 2. 源库 → 目标表映射总览

| 目标表 | 来源 | 说明 |

## 3. 各表详细设计

### 3.1 `contacts`（联系人主表）

每个账号、每个联系人一行，主键 **`(account, username)`**。

**保留 / 新增字段：**

| 字段 | 来源 | 含义 |
|------|------|------|
| `account` **(PK)** | 配置 `ACCOUNTS[].account` | 短标签：`personal` / `work` |
| `username` **(PK)** | contact.username | 业务唯一标识（在该 account 内） |
| `type` **(新增)** | username + local_type 推导 | `person` / `chatroom` / `official` / `openim` |
| `is_friend` **(新增)** | local_type 推导 | 1=好友，0=群里认识的非好友 |
| `alias` | contact.alias | 微信号 |
| `nick_name` | contact.nick_name | 昵称 |
| `remark` | contact.remark | 备注名 |
| `description` | contact.description | 你写的好友描述 |
| `signature` **(新增)** | extra_buffer #4 | 个性签名 |
| `gender` **(新增)** | extra_buffer #2 | `0`未知 / `1`男 / `2`女（已用数据验证） |
| `country` **(新增)** | extra_buffer #5 | 国家/地区，如 CN |
| `province` **(新增)** | extra_buffer #6 | 省份 |
| `city` **(新增)** | extra_buffer #7 | 城市 |
| `labels` **(新增)** | extra_buffer #30 → contact_label 翻译 | 标签**名**数组（JSON），如 `["标签A","标签B"]`（已内联，无需 JOIN） |
| `head_img_url` | contact.big_head_url | 头像 URL |

**丢弃字段：** `id`、`local_type`（已转 type/is_friend）、`encrypt_username`、`flag`、
`verify_flag`、`delete_flag`（先过滤后丢）、`remark_quan_pin`、`remark_pin_yin_initial`、
`pin_yin_initial`、`quan_pin`、`small_head_url`、`head_img_md5`、`chat_room_notify`、
`is_in_chat_room`、`chat_room_type`、`extra_buffer`（已拆解）。

**`type` 推导规则：**
- `@chatroom` 或 `@im.chatroom` 结尾 → `chatroom`（后者为新格式大数字群 ID，曾误标为 person，已修复）
- `@openim` 结尾 → `openim`（企业微信）
- `gh_` 开头 → `official`（公众号）
- 其余 → `person`

**保留哪些行（陌生人处理，见 §6 决策 1）：**
- ✅ 好友（local_type 0/1，非群）：2162 个
- ✅ 群聊实体（local_type 2）
- ✅ 公众号 / 企业微信
- ✅ **出现在群成员表里的群成员**（local_type 3，约 23788 个）→ `is_friend=0`
- ❌ **真·孤立陌生人**（local_type 3 且不在任何群、非好友，约 5597 个）→ 丢弃

> 保留群成员是为了让 `chatroom_members` 关系不空指针，并能知道群里都有谁。

### 3.2 `chatrooms`（群聊信息表）

| 字段 | 来源 | 含义 |
|------|------|------|
| `account` **(PK)** | 配置 | 短标签：`personal` / `work` |
| `username` **(PK)** | chat_room.username | 群 ID（同 contacts.username，在该 account 内） |
| `group_owner` | chat_room.owner | 群主 wxid（源字段 `owner`；**勿与 `account` 混淆**） |
| `announcement` | chat_room_info_detail.announcement_ | 群公告纯文本 |
| `announcement_time` | chat_room_info_detail.announcement_publish_time_ | 公告发布时间（Unix 秒） |

**丢弃**：`id`/`room_id_`、`ext_buffer`、`xml_announcement_`、`chat_room_status_`、`announcement_editor_`。

### 3.3 `chatroom_members`（群成员关系，直接用 username）

> 一次性 JOIN 解析：`room_id → chat_room.username`，`member_id → contact.username`，
> 落库只存 username，**不再保留数字 id**。约 11 条找不到 contact 的孤立引用会被跳过。

| 字段 | 来源 | 含义 |
|------|------|------|
| `account` **(PK)** | 配置 | 短标签：`personal` / `work` |
| `room_username` | chatroom_member.room_id 解析 | 群 ID（FK → chatrooms） |
| `member_username` | chatroom_member.member_id 解析 | 成员 wxid（FK → contacts） |

主键：**`(account, room_username, member_username)`**。

### 3.4 `messages`（聊天记录，合并所有分表）

把全部 `Msg_<md5>` 合并成一张表，用 `chat_username` 标识会话归属。

> ⚠️ **重要：同一会话被按时间分区存到多个 `message_<N>.db` 分片**（实测一个会话可同时
> 出现在 message_0/1/2.db，分别存不同时间段的消息）。因此：
> - `local_id` **只在单个分片内自增**（每个分片都从 1 开始），**跨分片会重复**，不能当全局键；
> - **`server_id` 在该 `account` 内唯一**（跨 account 可碰撞，故去重键为 `(account, server_id)`），用于去重与媒体/引用回查；
> - 构建时必须遍历**所有分片**合并，否则会漏掉旧消息（例：某好友会话在 message_0.db 仅 260 条，
>   加上 message_2.db 的 49 条才是完整的 309 条）。

| 字段 | 来源 | 含义 |
|------|------|------|
| `id` **(PK, 新增)** | 自增 | 全局 surrogate 主键（跨号唯一） |
| `account` **(新增)** | 配置 | 短标签：`personal` / `work` |
| `chat_username` **(新增)** | Msg 表名 → username 反查 | 属于哪个会话（人或群）；**在该号内** |
| `local_id` | Msg.local_id | 分片内本地 ID（**非全局唯一**，仅作参考） |
| `server_id` | Msg.server_id | 服务器消息 ID；**在该号内唯一**（去重 + 媒体/引用回查）；=0 为本地消息 |
| `timestamp` | Msg.create_time | Unix 秒级时间 |
| `sender_username` **(新增)** | real_sender_id → Name2Id 解析 | 发送者 wxid；自己为 `me` |
| `is_self` **(新增)** | 由 sender 推导 | 是否自己发送（0/1） |
| `type` **(转换)** | local_type → 文字标签 | `text`/`image`/`voice`/`video`/`sticker`/`link`/`quote`/`location`/`card`/`call`/`system` |
| `content` | message_content（zstd 解码后解析） | **可读文本**（见下方按类型处理） |
| `media_ref` **(新增)** | message_content XML 提取 | 媒体外链引用 JSON；非媒体消息为 NULL |
| `reply_to` **(新增)** | refermsg/svrid 提取 | 引用消息指向的**被引用消息 `server_id`**；非引用消息为 NULL |
| `reply_quote` **(新增)** | refermsg 快照（仅兜底）| 仅当 `reply_to` 在本库 JOIN 不到原消息时，才存被引用原文快照 JSON `{sender,type,content,time}`；能 JOIN 到则为 NULL |

**唯一约束**：**`(account, server_id)`**（部分唯一索引，`WHERE server_id != 0`）。
`reply_to` 自关联须 **同号**：`o.account = q.account AND o.server_id = q.reply_to`。

**`content` / `media_ref` 按消息类型处理：**

| type | content | media_ref（JSON）| reply_to |
|------|---------|------------------|----------|
| text | 文本正文 | NULL | NULL |
| quote（49 + appmsg type=57）| 我实际发的话（`<title>`）| NULL | 被引用消息的 svrid |
| link（49） | 标题 + 链接（可读，**保留为文本语料**）| `{url,title,des,...}` | NULL |
| location（48）| 地点名/label | `{x,y,poiname,label}` | NULL |
| card（42）| 对方昵称 | `{username,nickname}` | NULL |
| image（3）| NULL | `{md5,aeskey,cdnurl,length}` | NULL |
| voice（34）| NULL | `{aeskey,voiceurl,voicelength,voicemd5}` | NULL |
| video（43）| NULL | `{md5,newmd5,aeskey,cdnvideourl,playlength}` | NULL |
| sticker（47）| NULL | `{md5,cdnurl,productid}` | NULL |
| system（10000/10002）| 系统文本（撤回提示等）| NULL | NULL |

> 即：图片/语音/视频/表情**不存原始数据**，只存 md5/aeskey/cdn 链接等引用；
> 链接/位置/名片这类**本身是文本**的，正文写进 `content` 当语料。

**引用消息（quote）的极简处理（你的决策）：**
- `type=quote`（识别 `local_type` 低32位=49 且 `appmsg/type=57`）。
- `content` 只存**我实际发的话**（appmsg `<title>`）。
- **不存被引用消息的原文副本**，只用 `reply_to` 记下被引用消息的 `server_id`。
- 取被引用原文时顺着指针自关联（**必须同号**）：
  ```sql
  SELECT q.content AS 我的回复, o.content AS 被引用原文
  FROM messages q
  LEFT JOIN messages o
    ON o.account = q.account AND o.server_id = q.reply_to
  WHERE q.type = 'quote';
  ```
- 兜底（能省就省，不能省不硬省）：构建时先落全部消息，再做一遍校验——
  若某条 quote 的 `reply_to` 在库内 **JOIN 得到**原消息 → `reply_quote` 留 NULL（省）；
  若 **JOIN 不到**（原消息已删/不在库）→ 把 `<refermsg>` 里的 `{displayname,type,content,createtime}`
  快照写进 `reply_quote`，避免引用上下文彻底丢失。
- 注意：引用对象可以是任意类型（实测有引用「位置」消息的），`reply_quote.type` 记录其原类型。

**丢弃字段：** `sort_seq`、`status`、`upload_status`、`download_status`、`server_seq`、
`origin_source`、`source`、`compress_content`、`packed_info_data`、`WCDB_CT_*`。

## 4. 媒体回查路径（精简库 → 原始库 / 磁盘）

非文本消息的原始数据不进 `governed.db`，但可用 `messages` 保留的键回查（已实测验证）。

> **双账号**：回查前先根据 `messages.account` 选定对应解密目录
>（personal → `wechat-decrypt-personal/decrypted/message/`，work → `wechat-decrypt-work/decrypted/message/`），
> 再在该目录下的 `media_0.db` / `message_resource.db` 里查。

### 语音（type=voice）
```
messages.account + messages.server_id
  ==  <对应号>/message/media_0.db / VoiceInfo.svr_id
                        → voice_data (silk 格式 BLOB)
```
（亦可用 `chat_name_id + local_id` 关联，但 `(account, server_id)` 更稳。）

### 图片 / 视频 / 文件（type=image/video/link）
```
messages.account + messages.server_id
  ==  <对应号>/message/message_resource.db / MessageResourceInfo.message_svr_id
                        → packed_info (含文件 MD5)
                        → 磁盘 .dat 文件（路径随号主账号目录而异）
                        → 需用项目 decode_image.py 解密（AES/XOR）
```

### CDN 重新下载
`media_ref` 里保留了 `cdnurl`/`voiceurl`/`cdnvideourl` + `aeskey`，
理论上也可走微信 CDN 重新拉取（需登录态，通常已失效，**优先用本地 .dat**）。

> 结论：`server_id`（+ `chat_username`/`local_id`）是回查主键，`media_ref` 是冗余补充。
> 二者都保留，确保未来任意时刻都能把媒体取回来。

## 5. 最终库结构一览（`governed.db`）

```
contacts(account PK, username PK, type, is_friend, alias, nick_name, remark,
         description, signature, gender, country, province, city,
         labels, head_img_url)

chatrooms(account PK, username PK,
          group_owner, announcement, announcement_time)
  -- group_owner = 群主 wxid（源 chat_room.owner）

chatroom_members(account PK, room_username, member_username,
                 PK(account, room_username, member_username))

messages(id PK, account, chat_username, local_id, server_id, timestamp,
         sender_username, is_self, type, content, media_ref,
         reply_to, reply_quote)
  UNIQUE INDEX (account, server_id) WHERE server_id != 0
  INDEX (account, chat_username), INDEX (reply_to)
```

**关系图：**
```
contacts(account, username) ──< chatroom_members(account, member_username)
chatrooms(account, username) ──< chatroom_members(account, room_username)
contacts(account, username) ──< messages(account, chat_username)     (会话对象)
contacts(account, username) ──< messages(account, sender_username)   (发送者；自己=me)
messages(account, reply_to) ──> messages(account, server_id)         (引用，同 account 自关联)
messages(account, server_id) ──> <account 对应>/media_0.db / message_resource.db / 磁盘 .dat
```

## 6. 已确认的决策（你的选择）

| # | 问题 | 决策 |
|---|------|------|
| 1 | 群内陌生人处理 | **丢弃真·孤立陌生人（5597）**，保留群成员（23788，`is_friend=0`）以维持群关系 |
| 2 | 公众号/企业微信推送 | **不纳入** messages |
| 3 | labels 字典表 | **不单独建表**，仅在构建时翻译名字，内联到 contacts.labels（存名字） |
| 4 | messages.sort_seq | **不保留**，按 `timestamp` 排序（`local_id` 跨分片不可靠，仅作参考） |
| 5 | 非文本消息内容 | **不存原始数据**，但保留 `media_ref` 外链 + `server_id` 回查键；链接/位置/名片的文本写入 content |
| 6 | 引用消息（type=quote）| 用 `reply_to` 存被引用 `server_id` 自关联回查；**仅当原文不在库**时才把快照存进 `reply_quote`（能省就省） |
| 7 | 双账号合并 | 两解密库合并进同一 `governed.db`；全表加 **`account`**（`personal`/`work`）；号主 wxid 仅配置 `owner_wxid`；主键/唯一键均带 `(account, …)`；`chatrooms.owner` → **`group_owner`**；详见 **`docs/下游迁移指南.md`** |
| 8 | 增量构建 | 日常更新用 **`--incremental`**：保留 governed.db，messages 按 **`build_meta`** 水位（每 `Msg_*` 表 `max_local_id`）只读新行；去重键 `(account, server_id)` + `(account, chat_username, local_id)`；源库全量重解密后用 **`--incremental --reset-meta`** 重扫对齐 |

## 7. 构建脚本与产出

构建脚本：项目根的 `build_governed_db.py`（只读源库 → 生成 `output/governed.db`）。

### 7.0 全量 vs 增量

| 命令 | 行为 |
|------|------|
| `python3 build_governed_db.py` | **全量**：删旧库，DROP 重建 |
| `python3 build_governed_db.py --staging-tmp` | 全量，但在 `/tmp` 写入后 mv（推荐，规避 WSL2 `/mnt` 慢盘） |
| `python3 build_governed_db.py --incremental` | **增量**：保留库；contacts/chatrooms/members 按 account 刷新；messages 只读 `local_id > build_meta.max_local_id` |
| `--incremental --account work` | 只更新 work 号，personal 不动 |
| `--incremental --reset-meta` | 不删库，忽略水位，重扫全部 `Msg_*`，靠 `INSERT OR IGNORE` 去重 |
| `--incremental --staging-tmp` | 复制现有库到 `/tmp` 增量构建，再 mv 回 output |

**`build_meta` 表**（构建内部，5 张表之一）：主键 `(account, msg_table)`，存每个 `Msg_<md5>` 源表已处理的最大 `local_id`。全量构建时同步写入，供下次增量使用。

**去重键（messages）**

- `UNIQUE(account, server_id) WHERE server_id != 0`
- `UNIQUE(account, chat_username, local_id)` — 覆盖 `server_id=0` 的本地消息，增量必需

**增量局限（已知）**

- 不处理消息撤回/删除同步（撤回后 governed 仍保留旧行）。
- `chatroom_members` 仅 `INSERT OR IGNORE`，不退群成员。
- 源库被**全新全量解密**替换且结构大变时，建议先全量重建，或 `--incremental --reset-meta`。
- 首次对**旧版无 `build_meta` 的库**做增量：脚本会自动去重 `(account, chat_username, local_id)` 并**从已有 messages 反推水位**，避免重扫全库。

**构建性能（脚本内，不改 schema）**

- text/system 消息走快路径，跳过 `interpret_message` 大分支。
- XML regex 预编译；quote 的 refermsg 只解析一次。
- 输出库 `PRAGMA journal_mode=WAL; synchronous=NORMAL`；WSL2 慢盘建议 `--staging-tmp`。
- 日志输出「去重跳过 N 条」（`INSERT OR IGNORE` 命中唯一键）；每 50 个会话表打印进度。
