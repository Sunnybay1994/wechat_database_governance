## 1. `row_factory`：让查询结果能用「列名」访问

### 默认是元组，只能用数字下标

`sqlite3` 查询结果**默认每行是一个普通元组（tuple）**，元组不记列名，只能按位置取值：

```python
conn = sqlite3.connect("x.db")
row = conn.execute("SELECT svr_id, local_id FROM VoiceInfo").fetchone()
# row = (234357043509410, 15)   ← tuple
row[0]          # ✅ 按位置
row["svr_id"]   # ❌ TypeError: tuple indices must be integers or slices, not str
```

### 设 `row_factory = sqlite3.Row` 后，列名/位置都能用

```python
conn = sqlite3.connect("x.db")
conn.row_factory = sqlite3.Row     # 关键一行
row = conn.execute("SELECT svr_id, local_id FROM VoiceInfo").fetchone()
row[0]          # ✅ 仍可按位置
row["svr_id"]   # ✅ 现在也能按列名
list(row.keys())  # ✅ 还能拿到所有列名
```

`sqlite3.Row` 是标准库自带的「行工厂」，它在内部额外记住了「每个位置对应哪个列名」。

### 关键认知

| 要点 | 说明 |
|------|------|
| **逐连接生效** | `row_factory` 是**每个连接各自的属性**，在 A 连接上设了**不会**传给 B 连接 |
| **不改数据** | 只影响「结果怎么取值」，查到的值本身完全一样 |
| **首选 Row** | `row["nick_name"]` 比 `row[7]` 可读得多，列顺序变了也不会错位 |

> 本项目踩过的坑：全局 `gconn` 设了 `Row`，但回查函数里**另开的连接**没设，
> 结果对那个连接的结果用 `row["svr_id"]` 直接报 `tuple indices must be integers`。
> 修复 = 给每个需要列名访问的连接都设上 `conn.row_factory = sqlite3.Row`。

## 2. 连接的关闭与资源释放

### 不 `close()` 会怎样

一个未关闭的连接会占用：一个**文件句柄** + 少量**内存**。但：

- **不会无限泄漏**：同名变量反复赋值时，旧连接会被 Python 垃圾回收（GC 时自动关闭）。
- **内核退出兜底**：关闭 Notebook 内核 / 进程结束时，操作系统回收所有句柄。
- 所以「资源永久无法释放」基本不会发生，只是**不够干净**。

### 只读连接几乎不会「锁库」

真正导致 `database is locked` 的是**挂着未提交的写事务**。只读连接（`mode=ro`）不拿写锁，
不阻止别人读，也不阻止你用别的工具打开同一个库。

### Notebook 里的权衡

把 `conn.close()` 放在**分析单元格结尾**有个副作用：**重复运行该格**时，第二次一开始连接已关，
直接报 `ProgrammingError: Cannot operate on a closed database`。

两种干净写法：

**方案 A — 每格用 `with` 自管理（推荐一次性脚本）**

```python
from contextlib import closing

with closing(sqlite3.connect(f"file:{DB}?mode=ro", uri=True)) as conn:
    conn.row_factory = sqlite3.Row
    rows = conn.execute("SELECT ...").fetchall()
# 出 with 块自动 close，既释放又不影响别的单元格
```

> 注意：`sqlite3` 原生的 `with conn:` 管的是**事务提交/回滚**，并不自动 close 连接；
> 要确保关闭就用 `contextlib.closing` 包一层。

**方案 B — 保留全局连接，最后单独放一个「收尾」单元格**（本项目采用）

```python
# 分析单元格：复用全局 gconn，不在此处 close → 可反复运行

# 末尾收尾单元格（全部分析做完再运行）：
try:
    gconn.close()
except NameError:
    pass   # 还没创建
```

> 小知识：对**已经关闭**的 sqlite 连接再次调用 `.close()` 是**安全的空操作**，不会报错。

## 3. 只读、防锁、避免副作用文件

读别人的库（尤其是正在被其他程序使用的库）时，强烈建议用**只读 + immutable**：

```python
def connect_ro(path):
    # mode=ro    : 只读打开
    # immutable=1: 承诺文件不会被改动 → 不创建 -wal/-shm，不加锁，最快
    return sqlite3.connect(f"file:{path}?mode=ro&immutable=1", uri=True)
```

要点：

- 必须带 `uri=True`，否则 `file:...?mode=ro` 这种 URI 参数不会被解析。
- `immutable=1` 能避开 WSL/网络盘上常见的 `locking protocol` / `disk I/O error`，
  且不会在源目录留下 `-wal`、`-shm` 临时文件（对"只看不改"的解密库很重要）。
- 代价：`immutable` 期间若源文件真的被改了，读到的可能是旧页；仅用于确认不会并发写的场景。

## 4. 参数化查询（防注入 + 防转义 bug）

**永远不要用字符串拼接把值塞进 SQL**，用 `?` 占位 + 参数元组：

```python
# ✅ 正确：值用 ? 占位
conn.execute("SELECT * FROM contact WHERE username = ?", (username,))

# ❌ 危险：拼接，遇到引号/特殊字符就崩，且有注入风险
conn.execute(f"SELECT * FROM contact WHERE username = '{username}'")
```

> 例外：**表名/列名不能用 `?` 占位**（占位符只能代值）。表名必须拼接时，
> 要么来自可信白名单，要么用 `[...]` 方括号包住：`f"SELECT * FROM [{table}]"`。
> 本项目的 `Msg_<md5>` 表名就是这么拼的（md5 值可信，不会注入）。

## 5. 批量写入：`executemany` + 事务

逐条 `execute` + 逐条 `commit` 会非常慢。正确做法是**攒一批 + 一次 executemany + 周期性 commit**：

```python
batch = [(a, b, c) for ... ]            # 先在内存里攒
out.executemany(
    "INSERT INTO messages (x, y, z) VALUES (?, ?, ?)", batch)
out.commit()                            # 每处理 N 个会话再 commit 一次
```

本项目 190 万→306 万条消息就是这样几分钟写完的。`commit` 太频繁（每行一次）会因为反复刷盘极慢。

## 6. 去重：部分唯一索引 + `INSERT OR IGNORE`

需求：`server_id` 全局唯一去重，但 `server_id=0`（本地消息）不参与去重。
用**部分唯一索引（partial unique index）**精确表达：

```sql
CREATE UNIQUE INDEX idx_msg_svr ON messages(server_id) WHERE server_id != 0;
```

配合 `INSERT OR IGNORE`，插到重复的非零 `server_id` 会被自动跳过，而 `server_id=0` 的行不受约束全部保留：

```python
out.executemany("INSERT OR IGNORE INTO messages (...) VALUES (...)", batch)
```

> 教训：一开始用了 `UNIQUE(chat_username, local_id)` 当去重键，结果发现微信把**同一会话按时间
> 分片**存到多个 `message_<N>.db`，`local_id` 每个分片都从 1 重新计数 → 跨分片碰撞 → 误删了 44 万条。
> **选去重键前，务必确认它是否真的全局唯一**（实测 `server_id` 跨分片零碰撞才是对的）。

## 7. 探查未知库结构的几招

```python
# 列出所有表
con.execute("SELECT name FROM sqlite_master WHERE type='table'")

# 看某表的字段（名/类型/是否主键）
con.execute("PRAGMA table_info(contact)")        # 返回 (cid, name, type, notnull, dflt, pk)

# 按前缀匹配表名（LIKE 里 _ 是通配符，匹配字面下划线要转义）
con.execute(r"SELECT name FROM sqlite_master "
            r"WHERE type='table' AND name LIKE 'Msg\_%' ESCAPE '\'")

# 快速抽样
con.execute("SELECT * FROM contact LIMIT 5")
```

> `LIKE 'Msg_%'` 里的 `_` 会匹配**任意单字符**！要匹配真正的下划线，必须
> `LIKE 'Msg\_%' ESCAPE '\'`，否则会多匹配出 `MsgX...` 之类的表。

## 8. 大整数 / BLOB 小注意

- **大整数**：微信 `server_id` 是 64 位整数（可达 ~9.2e18）。SQLite 的 `INTEGER` 是 8 字节有符号，
  能装下；Python `int` 无限精度，写入时若超过 2^63-1 才会 `OverflowError`（本项目未触发）。
- **BLOB 长度别整列拖回内存**：想知道二进制字段多大，用 SQL 端的 `length()`：

```python
con.execute("SELECT length(voice_data) FROM VoiceInfo WHERE svr_id=?", (sid,))
# 比 SELECT voice_data 再 len() 省内存得多
```

## 9. 用「自然键」自关联表达引用关系

引用消息（回复某条消息）不必另建关系表，存被引用消息的**全局唯一键**即可，查询时自关联：

```sql
SELECT q.content AS 我的回复,
       COALESCE(o.content, q.reply_quote) AS 被引用内容
FROM messages q
LEFT JOIN messages o ON o.server_id = q.reply_to AND o.server_id != 0
WHERE q.type = 'quote';
```

`LEFT JOIN` 保证「原文已删/不在库」时这条引用消息也不丢，再用 `COALESCE` 回退到快照字段。

| 想做的事 | 写法 |

| 取 BLOB 大小 | `SELECT length(col)` |
```
